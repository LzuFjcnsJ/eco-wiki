这个站不是一个「写死的网页」，而是一个**由 Markdown 文件驱动的 Wiki**。
你不需要懂前端，只要会写 Markdown，就能往里面加内容。

:::tip[一句话总结]
在 `src/content/docs/` 里放一个新的 `.md` 文件，站点就会自动多出一章 ——
目录、卡片、搜索索引、上一篇 / 下一篇全部自动更新。
:::

## 三种改法：挑一种顺手的

### 一、在浏览器里改（不用装任何东西）

1. 打开要改的那一页，滚到最下面，点 **「在 GitHub 上编辑本页」**
2. 网页上直接改 Markdown
3. 滚到底，写一句「改了什么」，点 **Commit changes**
4. 等一两分钟，线上自动更新

不是仓库成员也没关系：GitHub 会让你 Fork 并自动开一个 Pull Request，
管理员合并后同样生效。加新内容也不用自己去翻路径 ——
章节目录页点「新建一章」，数字遗产页点「新建一条」，GitHub 会替你建好文件。

:::tip[这一条是留给下一届的]
你不可能永远维护这个站。**让下一个人能在浏览器里直接改**，
比写一份再详细的交接文档都管用 —— 所以每篇文章底部的那个「在 GitHub 上编辑本页」
不是装饰，它是整套设计里最要紧的一环。
:::

### 二、本地改（一次要改很多时更快）

```bash
git clone <仓库地址> && cd eco-wiki
npm install
npm run dev      # 本地预览，改文件即时刷新
npm run build    # 提交前跑一遍，front-matter 写错会在这里报错
```

### 三、不会用 Git 的兜底

把改好的内容交给现任负责人代为提交。

:::warn[别把内容留在聊天记录里]
「我发群里了」不算交接。聊天记录会沉、会丢、换手机就没了。
只要内容没进仓库，下一个人要用的时候，就等于从来没写过。
:::

## 目录结构

```text
eco-wiki/
├── site.config.ts              ← 站点名、域名、仓库地址（交接时改这里）
├── CONTRIBUTING.md             ← 完整贡献指南
├── src/
│   ├── content.config.ts       ← 内容字段的校验规则（一般不用改）
│   ├── content/docs/           ← 教程正文：一个文件 = 一章
│   │   ├── writing.md
│   │   └── photography.md …
│   ├── content/legacy/         ← 数字遗产档案：一个文件 = 一条
│   ├── pages/                  ← 页面模板（一般不用改）
│   └── styles/                 ← 配色与排版（改外观时才动）
└── public/                     ← 静态资源，如 favicon
```

## 新增一章：三步

### 1. 新建文件

文件名就是网址。比如新建 `src/content/docs/venue.md`，它的访问地址就是 `/wiki/venue/`。

建议用英文小写 + 连字符，避免中文文件名带来的编码问题。

### 2. 写 front-matter

文件开头两行 `---` 之间是「元信息」，站点靠它生成卡片和目录：

```yaml
---
title: 场地申请流程          # 必填，卡片标题，建议不超过 60 字
summary: 借教室、借报告厅的完整步骤   # 必填，卡片摘要，建议不超过 160 字
chapter: 10                 # 必填，章节号 —— 决定排序和显示的数字
group: workflow             # 必填，core | workflow | reference
icon: 🏛️                    # 选填，卡片右上角的图标
tags: [场地, 流程]           # 选填，标签，目录页会自动汇总
status: draft               # 选填，stable | review | draft
updated: 2026-09-26         # 选填，最后更新日期
maintainer: 张三             # 选填，默认「宣传部负责人」
---
```

:::warn[三个字段最容易填错]
**chapter** 必须是正整数，且不要和已有章节重复 —— 它决定你在目录里的位置。

**group** 只能是 `core`、`workflow`、`reference` 三者之一，写别的会导致构建失败。

**文件名** 一旦确定就尽量别改，改了等于换了网址，别人收藏的链接会失效。
:::

### 3. 写正文

front-matter 之后就是正文，用标准 Markdown 写：

````markdown
## 二级标题（会出现在右侧目录里）

### 三级标题（也会出现在目录里，缩进一级）

- 普通列表项
- **加粗**、`行内代码`、[链接](https://example.com)

| 表格 | 也会被自动加上滚动容器 |
|---|---|
| 手机端不会撑破布局 | 是的 |

- [ ] 任务清单是可以勾选的
- [x] 而且会记住勾选状态
````

## 特殊块：红线 / 提示 / 正误对比

原始的细则文档里大量使用「红线规则」「正确 vs 错误」这类强调块。
本站用 `:::` 容器语法来表达，渲染出来是带颜色和标记的卡片。

```markdown
:::danger[红线规则]
这是红色的危险块，用来写不可逾越的规则。
:::

:::tip[提示]
绿色提示块。
:::

:::warn[注意]
黄色警告块。
:::

:::info[说明]
鼠尾草色的中性说明块。
:::

:::good[正确做法]
对比组里的正面示例。
:::

:::bad[错误做法]
对比组里的反面示例。
:::
```

可用的类型一共六种：`danger`、`warn`、`tip`、`info`、`good`、`bad`。
方括号里是标题，不写就用默认标题。

## 自动生效的东西

改完内容后，下面这些都会自动更新，**不需要手工维护**：

| 能力 | 来源 |
|---|---|
| 目录页卡片与分组 | 每个文件的 front-matter |
| 全局搜索（右上角或按 `/`） | 构建时生成的 `search-index.json` |
| 右侧「本页目录」 | 正文里的 `##` 和 `###` 标题 |
| 上一篇 / 下一篇 | `chapter` 的排序 |
| 标签云 | 所有文件的 `tags` 汇总去重 |

## 本地预览与发布

```bash
npm install       # 第一次运行时安装依赖（需要 Node 22+）
npm run dev       # 本地预览，改文件会即时刷新
npm run build     # 构建到 dist/，产出的就是可直接托管的静态文件
```

**平时不需要手动发布。** 仓库里配好了自动构建（`.github/workflows/deploy.yml`）：
往 `main` 分支推一次，或者在 GitHub 网页上点一次 Commit，就会自动重新构建并上线，
大约一两分钟。发布位置怎么配、交接怎么做，见仓库根目录的 `CONTRIBUTING.md`。

:::warn[确认没有报错再提交]
如果 front-matter 少填了必填字段，或者 `group` 写错，构建会直接失败并指出是哪一行。
本地 `npm run dev` 能正常打开，基本就没问题。
:::

## 往「数字遗产」档案里加一条

除了教程正文，站上还有一个**编年档案**（`/legacy/`）。它和正文是两套内容，放在不同目录：

```text
src/content/legacy/
├── _template.md            ← 模板，以 _ 开头，不会被收录
├── 2026-v1-builder.md
└── 2026-in-office.md
```

流程和写文章一样：复制 `_template.md`，改成 `年份-简短标识.md`，填字段。

```yaml
---
name: 王五
role: 宣传部负责人
cohort: 2027 届
year: 2026
lesson: 规则是死的，遇到没写过的情况，先问再做
stage: in-office        # in-office 在任 / alumni 已毕业
placeholder: false
---
正文可以留空，也可以多写几句当时的处境。
```

:::tip[这个档案是按年份往前长的]
不要把它当成一次性的纪念册。**每一届在任时就该写一条** ——
当时遇到的、往届没写过的情况，正是最有价值的部分。毕业之后还可以回来补。
只要宣传部还在，这个列表就会一直往下排。
:::

:::warn[内容没写全就标 placeholder]
姓名或寄语还没定下来时，把 `placeholder: true` 打开，页面上会显示「待补充」标记，
而不是让别人误以为这就是最终内容。
:::

## 改内容时的几条建议

1. **别删别人的署名。** 追加修改时在版本日志里记一行，注明改了什么。
2. **红线规则只增不减。** 如果某条规则不再适用，先改成 `:::warn` 并注明原因，不要直接删。
3. **状态别乱标。** `stable` 表示可直接执行；还没验证过的内容请标 `draft`。
4. **一篇文章只讲一件事。** 内容变长了就拆成两篇，比堆在一篇里好查。
